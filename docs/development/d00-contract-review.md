# D00：遥测契约决策、矛盾及验收清单

状态：设计评审草案，未实现、未冻结；2026-11-05。范围是本仓库 Rust 设备数据模型引擎，不改变用户要求的后端语言，不引入 AIOS 的 Bun / Hono 技术基线。依据 [服务边界](../architecture/data-engine-scope.md)、[P0 入站契约](../specifications/p0-telemetry-contract.md)、[设备业务模型](../specifications/device-business-model.md)、[存储契约](../specifications/storage-adapter-contract.md) 和 [外部库映射](../specifications/external-tsdb-reference-mapping.md)。

D00 是开发前的契约评审，不是 D01 代码、数据库能力测试、外部集成或自动关闭任务。当前仓库没有可验证的产品实现。候选规则需与真实网关消息、时钟及重传机制核对，经评审后更新权威规范和机器可读契约。

测量、质量事件分离与幂等候选细化见 [D00-B/C 专题方案](d00-measurement-quality-and-idempotency.md)；仍属待评审设计。

## 1. 目标和交付门槛

**目标**：让同一输入在网关、引擎、存储和上层视图中有一致解释；做到可以写出正反样例与故障测试，而不是仅列功能名称。

D00 完成需同时具备：
1. 本文件所有 P0 决策项明确为 accepted / rejected / deferred，记录决策依据、修订、影响及负责人；未定项不能被 Schema 静默固化。
2. 权威 P0 遥测规范、设备视图、WAL 与存储规范消除相关矛盾，标注版本及兼容策略。
3. 具备经过评审的机器可读 Schema / API 契约（包括字段边界、负例和错误格式）；Schema 仅负责结构，授权、绑定生效时间、幂等及 WAL 等动态规则需独立验证。
4. 两台泵正反样例和本文件测试矩阵运行并有命令、环境、结果及提交 SHA；当前仅有文档时，任何未运行项均标记 NOT_RUN。
5. 网关实际样例与能力至少完成一次差异核对；没有真实网关时可完成模拟契约评审，但实际集成仍为 BLOCKED，不得声称验证通过。

## 2. 已确认边界

- 设备 / 模型 / 资源 / 质量 / 时间及历史数据由本引擎提供；用户、角色、业务权限、审批、告警、控制及 AI 体验由上层负责。引擎验证服务身份及可信范围，不信任客户端自报 tenant / role。
- P0 每条消息是一台设备、一个模型版本、一个绑定版本；点位整消息通过或拒绝。默认网关上报工程值，引擎不重复倍率换算。
- accepted_volatile / accepted_durable 区分；durable 只代表本地应用 WAL 达同步边界，不能宣称历史已提交或远端已写。
- DuckDB 2.0.0 是当前本地目标；SQLite 等元数据后端和外部 TSDB 为可选方向，不在本文件改默认。
- read-only 外部数据库引用不是 P0 网关写入路径，不天然享有 observation_id、WAL、采集确认、订阅连续性或可恢复语义。

## 4. 幂等语义方案（候选）

消息唯一范围为可信 tenant_id + source_id + source_epoch + message_id；tenant_id 从已验证服务上下文获取，不由请求体决定。未经认证或校验未通过的消息不得创建业务上的 durable 接收记录。

**建议的顺序**：
1. 验证主体和范围、消息大小与基本结构；定位声明的设备、模型、绑定版本。
2. 整消息检查所有点位，拒绝重复 property、未知属性及非法时间 / 类型；任一点无效则整体无副作用。
3. 建立固定版本的“业务内容表示”，包含设备、模型 / 绑定版本、各点标识、工程值、源时间、时钟来源、序列、质量与来源码；不包含每次传输会变化的 request_id、replayed 和服务端 received_at。
4. 按规范化算法求 payload_hash；同一个 key 用持久化 hash 比较：相同内容返回原 ingest_id，不同内容拒绝并报告冲突。
5. 同 key 并发时先解决 pending 状态及崩溃恢复，不能两个请求各产生独立 observation_id / durable ACK。首次接受时生成 observation_id 并随消息写入 WAL；重试和重放沿用。

**尚未确定 / 禁止臆定**：JSON 对象 key 排序、points 顺序是否无关、缺省与 null、Unicode 规范化、数值 1 / 1.0 / -0 及高精度整数、额外字段、未知字段处理、算法升级、hash 碰撞处理。建议在最终规范中指定语义、算法版本和字节级黄金样例，并由 Rust 与至少一个真实网关语言实现交叉验证；不能只依赖序列化库默认行为。完成前不得声称跨实现幂等已解决。

## 5. 从两台泵出发的契约向量

固定已发布模型 pressure: float64、单位 MPa；两台泵资源独立；网关输出 0.42 MPa。示例只描述语义，不是现场地址或正式 Schema。

| 向量 | 输入 / 故障 | 可观察结果 |
|---|---|---|
| V01 | 泵 A 合法压力消息 | 独立观测 A、视图显示 0.42，源时间 / 质量保留 |
| V02 | 泵 B 使用相同模型独立上报 | A / B resource_id、最新值及租户范围不串用 |
| V03 | 同消息重试且仅 replayed 变化 | 同 ingest_id；不产生第二个逻辑观测；持久前后语义依模式区分 |
| V04 | 同 key 修改 pressure 数值或源质量 | 返回冲突；历史 / latest 不被覆盖 |
| V05 | 含一个合法点和一个未知点 | 422 整消息拒绝，WAL、latest 和历史均无该消息副作用 |
| V06 | 网关值为 0.42，绑定倍率作为来源配置 | 不再次计算成 0.0042；需要 raw 模式时另立契约 |
| V07 | 先采样 t=2，后补传 t=1 | 合法历史可含两个事实，latest 保持 t=2 |
| V08 | 未采样设备 / 设备断线 | 前者 unknown / null；后者保留旧值与原采样时间并更新质量状态 |
| V09 | 源时钟未来漂移 / 旧绑定有效区间无法证明 | 依策略拒绝 / 隔离；不得覆盖正常 latest |
| V10 | 超出可信范围的设备查询 / 订阅 | 目录、视图、聚合和流均拒绝或按统一隐藏策略，不泄露资源 |
| V11 | 要求 durable，但 WAL 写满 / sync 失败 | 不得返回 durable；明示失败及重试语义 |
| V12 | 非本引擎管理的数据库没有质量与 observation ID | 返回 unknown / 能力限制；不能声称无损去重或 good-only 完整 |

必须分别给出具体请求、响应、执行前后状态及重复次数；所有示例单位、时间、地址仅测试数据。

## 6. WAL 与事务故障注入矩阵

| 故障点 | 客户端可能看到 | 必须验证的恢复行为 |
|---|---|---|
| 写 WAL 前 | 无 ACK / 失败 | 重试同 key；不遗留已接受事实 |
| 追加但未达到同步边界 | 未收到 durable | 只恢复可校验记录；无同步保证的记录不能视为已确认 |
| WAL 同步后、ACK 前 | 客户端超时 | 重试返回同 ingest_id；不得生成新观测 |
| DuckDB 事务未提交 | durable 已返回但历史 pending | 原子回滚，重放 |
| 历史 + applied_message + 死区基准已提交，checkpoint 未提交 | 历史可能已可查 | 判重防重复；推进 checkpoint |
| 外部目标已提交、响应丢失 | target unknown | 仅经验证幂等可重试，否则查回 / 隔离；不假设远端失败 |
| 磁盘满 / 日志中间损坏 | 明确错误 | 不吞掉已确认 WAL；阻止跨损坏段错误推进 |

每项使用独立发送清单记录 key、输入摘要、网关接收结果、实际历史 / 去重 / latest / checkpoints、恢复耗时和数据缺口；进程 kill -9 与目标文件系统 / 硬件断电分别测试。只有实际确认 WAL 同步并完成故障测试，才可以对相应环境报告 durable 验证结果。
